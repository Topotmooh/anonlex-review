## 1. ОБЛАСТЬ ПРИМЕНЕНИЯ

Настоящая Методика устанавливает порядок автоматизированного выявления, классификации и обезличивания персональных данных (далее — ПДн) и иных конфиденциальных сведений в текстовых документах с использованием программного комплекса «ЛАСТИК» (далее — Система).

Методика применяется при:
- подготовке документов к передаче в системы искусственного интеллекта (LLM);
- обезличивании документов для целей тестирования, аналитики и машинного обучения;
- обеспечении соответствия обработки ПДн требованиям Федерального закона от 27.07.2006 № 152-ФЗ «О персональных данных»;
- формировании доказательственной базы должной осмотрительности оператора ПДн при проверках регуляторных органов и в судебных разбирательствах.

**Поддерживаемые форматы входных документов:** DOCX, DOC, PDF (текстовый слой и сканы с OCR), XLSX, TXT, CSV, HTML.

## 3. ТЕРМИНЫ И ОПРЕДЕЛЕНИЯ

| Термин | Определение |
|---|---|
| **ПДн (персональные данные)** | Любая информация, относящаяся к прямо или косвенно определённому физическому лицу (ст. 3 152-ФЗ) |
| **Обезличивание ПДн** | Действия, в результате которых становится невозможным без использования дополнительной информации определить принадлежность ПДн конкретному субъекту (ст. 3 152-ФЗ) |
| **Плейсхолдер** | Символьная метка вида `[КАТЕГОРИЯ_номер]`, заменяющая исходное значение ПДн в обезличенном документе |
| **Маппинг** | Словарь соответствий «исходное значение ↔ плейсхолдер», хранящийся в зашифрованном хранилище (Vault) |
| **Vault (Хранилище)** | Зашифрованное хранилище маппингов с использованием алгоритма AES-256-GCM |
| **Акт экспертной обработки** | Юридически значимый документ, формируемый Системой по результатам обработки, содержащий хеш-суммы SHA-256, реестр выявленных ПДн и вердикт верификатора |
| **Вердикт верификатора** | Результат автоматической проверки обезличенного текста на остаточные ПДн: `CLEAN`, `REVIEW`, `SUSPICIOUS` |
| **Дело (Case)** | Логическая единица, объединяющая несколько документов со сквозным маппингом (один человек = один плейсхолдер во всех документах дела) |
| **Оператор** | Пользователь Системы, инициирующий обработку документов |
| **Officer** | Пользователь с расширенными правами, имеющий доступ к деанонимизации |

## 4. ОПИСАНИЕ ПРОЦЕССА ОБРАБОТКИ

### 4.1. Общая схема

Процесс обработки документа в Системе «ЛАСТИК» состоит из следующих этапов:

### 4.2. Этап 1. Загрузка документа

- Оператор загружает файл через веб-интерфейс или API.
- Система вычисляет контрольную хеш-сумму **SHA-256** исходного файла.
- Проверяется формат и размер файла (макс. 20 МБ).
- Файл помещается во временное хранилище, доступное только в рамках сессии обработки.

### 4.3. Этап 2. Извлечение текста

В зависимости от формата документа применяются различные методы:

| Формат | Метод извлечения |
|---|---|
| DOCX | Парсинг XML-структуры OOXML, извлечение параграфов и таблиц |
| DOC | Конвертация в DOCX через LibreOffice, далее как DOCX |
| PDF (текстовый слой) | Извлечение через PyMuPDF (MuPDF) |
| PDF (скан) | OCR через Tesseract 5.x с поддержкой русского языка |
| XLSX | Построчное извлечение текста из ячеек через openpyxl |
| TXT/CSV/HTML | Прямое чтение с нормализацией кодировки UTF-8 |

### 4.4. Этап 3. Выявление сущностей (NER)

Система использует **гибридный движок**, сочетающий три уровня анализа:

#### Уровень 1: Регулярные выражения (Regex)
Применяется для структурированных данных с чёткими паттернами:
- ИНН (10/12 цифр), КПП, ОГРН, БИК
- Банковские счета (20 цифр), номера карт (16 цифр)
- Паспортные данные (серия + номер)
- СНИЛС, полисы ОМС
- Email, URL, IP-адреса, MAC-адреса
- Номера договоров, даты, суммы

#### Уровень 2: Статистический NER (Named Entity Recognition)
Применяется для неструктурированных сущностей:
- ФИО (включая склонения и инициалы)
- Названия организаций (включая полные формы в верхнем регистре)
- Адреса (географические и почтовые)
- Диагнозы и медицинские термины

Используется библиотека **Natasha** (адаптированная для русского языка) с дообучением на отраслевых корпусах.

#### Уровень 3: Словарь организации
Пользовательские правила, добавляемые вручную или выученные на основе предыдущих обработок:
- Специфические номера договоров
- Внутренние идентификаторы
- Отраслевые термины

**Всего поддерживается 37 категорий ПДн**, объединённых в группы:
- **Идентификаторы личности** (ФИО, паспорт, СНИЛС, полис ОМС, водительское удостоверение)
- **Финансовые данные** (ИНН, КПП, ОГРН, БИК, счета, карты, IBAN, SWIFT)
- **Контактные данные** (адрес, телефон, email, URL)
- **Цифровые идентификаторы** (IP, MAC, криптокошельки, никнеймы)
- **Транспорт** (госномер, VIN, ПТС/СТС)
- **Медицинские данные** (диагнозы, биометрия)
- **Юридические данные** (номера договоров, лицензии, кадастровые номера)

### 4.5. Этап 4. Замена на плейсхолдеры

Каждой выявленной сущности присваивается плейсхолдер формата `[КАТЕГОРИЯ_номер]`, где:
- **КАТЕГОРИЯ** — код категории на русском языке (например, `ФИО`, `ИНН`, `КОМПАНИЯ`)
- **номер** — порядковый номер сущности в рамках категории

**Пример:** `Иванов Иван Иванович` → `[ФИО_1]`, `ООО "Ромашка"` → `[КОМПАНИЯ_2]`

При работе в режиме **Дела (Case)** применяется сквозной маппинг: одна и та же сущность во всех документах дела получает один и тот же плейсхолдер.

### 4.6. Этап 5. Верификация «Чистый лист»

После замены Система проводит контрольную проверку обезличенного текста по 19 правилам верификации:

| Вердикт | Условие | Действие |
|---|---|---|
| **CLEAN** | 0 находок остаточных ПДн | Документ готов к передаче |
| **REVIEW** | Найдены некритичные фрагменты (например, косвенные идентификаторы) | Рекомендована ручная проверка |
| **SUSPICIOUS** | Найдены критичные фрагменты (явные ПДн) | Требуется обязательная правка |

### 4.7. Этап 6. Запись в журнал аудита

Каждая операция обработки записывается в неизменяемый журнал со следующими полями:
- Имя оператора
- Имя файла и его SHA-256
- Количество замен
- Временная метка (UTC)
- Статус операции (успех/ошибка)

Журнал хранится в базе данных SQLite с поддержкой целостности через WAL-режим.

### 4.8. Этап 7. Запись в Vault

Маппинг «исходное значение ↔ плейсхолдер» шифруется алгоритмом **AES-256-GCM** с уникальным ключом на каждую операцию и сохраняется в Vault. Доступ к деанонимизации имеет только пользователь с ролью **Officer**, и каждое такое действие фиксируется в журнале с указанием причины.

### 4.9. Этап 8. Формирование Акта экспертной обработки

По завершении обработки Система формирует **Акт автоматизированной экспертной обработки данных**, содержащий:

1. **Основание проведения обработки** — ссылки на ГОСТ Р 56939-2024 и Приказ ФСТЭК № 240
2. **Объект исследования** — имя файла и SHA-256 исходного файла
3. **Результаты анализа** — количество проверенных категорий, выявленных фрагментов, применённых правил верификации, вердикт
4. **Сформированный объект** — имя обработанного файла и его SHA-256
5. **Реестр выявленных признаков ПДн** — таблица с категориями, исходными значениями, плейсхолдерами и количеством вхождений
6. **Заключение** — ссылка на ст. 84-87 ГПК РФ и ст. 82-86 АПК РФ
7. **Подпись ответственного оператора** — поле для ручной подписи или УКЭП

Акт формируется в форматах **HTML** (для просмотра и печати) и **JSON** (для машинной обработки).

## 5. КРИТЕРИИ КАЧЕСТВА

Качество работы Системы оценивается по трём метрикам:

| Метрика | Формула | Целевое значение |
|---|---|---|
| **Precision (Точность)** | TP / (TP + FP) | ≥ 95% |
| **Recall (Полнота)** | TP / (TP + FN) | ≥ 95% |
| **F1-Score** | 2 × (Precision × Recall) / (Precision + Recall) | ≥ 95% |

Где:
- **TP** (True Positive) — верно выявленные ПДн
- **FP** (False Positive) — ложные срабатывания
- **FN** (False Negative) — пропущенные ПДн

Бенчмарк проводится на эталонном корпусе из N документов с ручной разметкой. Результаты публикуются в дашборде качества и доступны через API `/api/quality/metrics`.

## 6. МЕРЫ БЕЗОПАСНОСТИ

### 6.1. Криптографическая защита

- **Хеширование:** SHA-256 для контроля целостности документов
- **Шифрование маппинга:** AES-256-GCM с уникальным nonce на каждую операцию
- **Хранение ключей:** изолированное хранилище Vault с разграничением доступа

### 6.2. Разграничение доступа (RBAC)

| Роль | Права |
|---|---|
| **Operator** | Загрузка документов, просмотр результатов, экспорт Акта |
| **Reviewer** | Все права Operator + ручная корректировка маппинга |
| **Officer** | Все права Reviewer + деанонимизация с указанием причины |

### 6.3. Изоляция данных

- Все операции выполняются **on-premise** (данные не покидают контур заказчика)
- Временные файлы удаляются после завершения сессии
- Поддержка работы без подключения к интернету

### 6.4. Соответствие требованиям ФСТЭК

Процессы разработки Системы соответствуют:
- **Приказу ФСТЭК № 240** от 01.12.2023
- **ГОСТ Р 56939-2024** (все 25 процессов безопасной разработки)
- Внедрены практики: SAST, DAST, SCA, код-ревью, управление уязвимостями
